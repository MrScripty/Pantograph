## Deciding findings

### RT-01 — Image loading has no enforced model-code authorization (blocking)

Rust owns `ModelLoadSecurityPolicy` in `crates/inference/src/model_contracts.rs:1260`, including deny/allow, network, revisions and decision identity. Transformers loading takes it through `PyTorchBackend::load_transformers_package` (`backend/pytorch.rs:1222`), rejects known required custom code when denied (`:1274`), and projects to the worker trust policy (`backend/pytorch_worker_contract.rs:143`). The Python Transformers loader forwards policy to tokenizer/model loaders (`torch/worker.py:837–882`). This review does not certify every Transformers authorization invariant.

The image path has no corresponding policy in `ImageGenerationPlanningInput`, `PlannedImageGenerationLaunchHandoff`, or `PyTorchGenerateImageRequest` (`image_generation_planner.rs:35`, `backend/pytorch_worker_image_contract.rs:159`). Its Python decoder rejects extra fields, including raw trust flags (`torch/worker_image_contract.py:12`; existing negative tests in `backend/pytorch_worker_image_contract_tests.rs:225`). Single and batch calls enter `load_diffusion_model` (`torch/worker.py:1741`, `:1645`), which reuses an existing pipeline by path alone (`:1058`) and then hardcodes `trust_remote_code=True` (`:1086`). Network/revision policy is also absent there.

Changing that boolean to false is insufficient. Installed Diffusers **0.37.0** source at `.venv/lib/python3.10/site-packages/diffusers/pipelines/pipeline_utils.py:915` resolves a local custom pipeline from model configuration before choosing its class. `pipeline_loading_utils.py:974` interprets `_class_name` list/tuple as local code; `:441` calls `get_class_from_dynamic_module`. Local component code is loaded similarly at `:410–426`. These local paths have no corresponding trust flag check. Thus local artifact readiness does not authorize package Python execution, and a remote-code flag is not the complete authorization mechanism.

The existing image Python suite replaces `load_diffusion_model` with a no-op (`backend/pytorch_worker_image_python_tests.rs:137`). It proves envelope/generation behavior but cannot prove loader authorization. The direct smoke script also calls the real loader (`scripts/diffusion_cli_smoketest.py:76`) and must share its enforcement.

First coherent repair contract: inference owns model-code permission; Pumas continues to supply package/code facts. The actual Diffusers load boundary must default closed, reject unauthorized local custom pipeline and component code before import or cache reuse, preserve permitted network/revision decisions, and prevent reuse of an earlier authorized executable pipeline under a later denied/different policy. Batch members must not inherit another member's greater authority. Ordinary built-in pipelines remain usable without granting custom-code permission. Malformed policy produces the existing declared typed failure, never Python truthiness-based permission. No new UI trust switch is justified by this finding alone.

Recommended first bounded implementation can enforce **closed-only image execution** at the loader until an end-to-end authorization source exists. This avoids inventing an Allow decision at the host. Exact minimal production write set: `crates/inference/torch/worker.py` and a narrowly scoped helper only if needed in existing `crates/inference/torch/worker_runtime.py`; regression owner `crates/inference/src/backend/pytorch_worker_image_python_tests.rs`. Keep deny logic at the effect boundary shared by envelope, batch and CLI consumers. If the integrator instead admits configurable authorization now, expand the coherent write set explicitly to `model_contracts.rs`, `image_generation_planner.rs`, `backend/pytorch_worker_contract.rs`, `backend/pytorch_worker_image_contract.rs`, `backend/pytorch_image_generation.rs`, `torch/worker_contract.py`, `torch/worker_image_contract.py`, their existing contract tests, and runtime-host handoff composition. A boolean-only patch must not be accepted.

### RT-03 — smallest coherent prerequisite: owned PyTorch text jobs and awaited replacement

Admit this inference-owned prerequisite before adding the host text branch. It has one result: an existing text stream cannot outlive the owner which must finish or cancel it before loading/replacing its model. The replacement bypass is concrete: `gateway.rs:512` calls synchronous `guard.stop()` and immediately replaces the backend, while `backend/pytorch.rs:2811` launches an unjoined shutdown thread. Fixing only direct PyTorch load/unload leaves that bypass open.

Mechanism: give the existing PyTorch backend one current text-job owner containing cancellation state and the retained `spawn_blocking` completion. The returned stream observes that job; dropping its receiver requests cancellation but does not discard the owner's completion handle. Completion can be shared between stream observation and lifecycle drain without joining a handle twice. Preserve one live text job; a second request must wait for the current job's terminal result or return an explicit occupied outcome, never replace its handle. No host/runtime registry is added. Load, reload and unload drain the owned job before changing module globals; ordinary replacement waits for accepted work rather than silently cancelling it. Explicit stop/backend switch requests cancellation and then awaits actual completion.

Make the backend stop contract awaitable and fallible, replacing the synchronous trait operation rather than retaining a best-effort PyTorch shutdown shim. Gateway `switch_backend`, `start` and `stop` must observe completion under the existing backend write ownership before replacing the box, changing model state or claiming stopped status. A failed stop leaves the old backend owned and preserves its failure; it does not instantiate/use the replacement. Existing legacy streams are covered because they register the same backend-owned job before returning their receiver, even though the gateway read guard later drops. Existing caller result propagation is part of this slice. Other production backend implementations migrate the trait signature around their existing stop mechanism; do not claim new sidecar lifecycle guarantees from this mechanical migration.

The worker checks cancellation before/after advancing its Python iterator. Its bounded channel send must also be cancellation-aware, so a full receiver buffer cannot prevent cooperative shutdown; a blocking-thread bridge to `select!` between send and cancellation is sufficient. The terminal `done` chunk is not published until the producer has returned successfully and its completion has been observed. Propagate Python errors and join panic/failure as typed failures. Premature EOF is not success; update the existing typed final collector accordingly. Receiver drop, explicit cancellation and normal completion converge on the same owned job termination; no shutdown thread is detached.

Progress limit: cancellation cannot interrupt a Python iterator step or Torch call that never returns. In that case stop/replacement remains pending, the current residency remains occupied, and no completed cancellation, unloaded model or reusable reservation is claimed. Do not invent a timeout, abort a running blocking task as if it stopped, or unload module globals underneath it. Hard bounded termination would require an independently admitted process boundary.
