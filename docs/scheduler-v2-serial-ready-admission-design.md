# Serial Ready admission boundary

Production main was checked at `038dacaaa98ebd007c32e13d4608726ca5ccf63a`; this branch starts at the independently reviewed CPU calibration commit `0bfa4df7`. No POC implementation is copied. The unavailable archive is not a prerequisite for fresh Rust contract work.

The smallest integration is an opt-in service constructor, never a builder on a previously cloned service. Every clone, worker handle and assignment repository must share one immutable execution mode. Before preparation or event claims, acquire serial admission. Waiting commands hold no store lock, event, assignment or runtime reservation. Reject legacy execution for that mode unless it participates in the same gate. Keep the existing default constructor, session admission priorities, starvation boosts and warm-reuse window unchanged.

After admission, use the authoritative first two dependency-ready runtime tasks in graph order, never skip an unsupported first task. Bound the complete population before cloning (128 tasks/records), each proof/task and exact input size. Require both tasks to use the same admitted run, exact artifact, CPU owner, effective thread settings and dependency environment. Capture both records, proofs, inputs and population order; call evidence providers outside the store lock. Revalidate the entire cohort immediately before Start. An owner-generation check at Start is advisory: execution must also validate loaded instance/settings when acquiring the actual runtime owner. No residency lease can be inferred from calibration.

For already resident singleton CPU workloads, compare qualified completed warm execution-plus-drain observations. Two serial orders have equal represented terminal service time; shorter-first minimizes the sum of the two represented completion times. Ties preserve graph order. This is a restricted empirical service objective, not an end-to-end dispatch prediction. Missing preparation/load/transfer/release costs are not zero and cannot be passed to the broader completion planner as complete timing.

The broker must enforce singleton membership for both anchors and peers; setting an anchor's maximum to one alone is insufficient. Hold serial ownership through actual host drain and matched reservation cleanup acknowledgement (assignment terminal state occurs earlier). Release before processing a continuation, then reacquire and recompute. Abandoned execution or unsuccessful cleanup permanently poisons the shared mode; deferred waiters must wake or refuse, never silently reopen it. A new explicit service construction is needed to recover.

The pure local contract uses nonblocking admission: Busy safely refuses before claims. Its preparation guard can be released before claims; promotion to a dispatch guard occurs before the first ownership mutation. Dropping that dispatch guard poisons the shared mode. The follow-up contract removes public unchecked release: a private, non-Clone ticket now binds the owned attempt/request/lease, held-owner validation, terminal drain and exact expected release event before accepting a matched lifecycle acknowledgement. The adapter still supplies actual drain and release semantics; see `scheduler-v2-bound-dispatch-contract-results.md`.

Current coverage: session capacities and priorities, queues, dependency Ready proofs, reservation custody, runtime ownership, broker batching and actual cleanup already exist. CPU calibration has bounded local warm timing and an actual loaded-instance/settings identity. Aggregate CPU throughput capacity, GPU capacity/timing, native batching, persistent residency guarantees, remote-node capacity and complete transition timing remain absent. Existing admission, session and runtime contracts remain authoritative.

Acceptance before wiring the mode: concurrent commands; refused Busy with no claims; service clones sharing poison; singleton peer-broker exclusion; caller drop and worker panic; cleanup failure after terminal mutation; continuation release/reacquisition; both Ready snapshots changing; input/proof/population changes; actual-owner changes at execution; incomplete/foreign/stale timing; stable ties and arithmetic overflow; and legacy/default compatibility. Deterministic host end-to-end tests must inspect actual dispatch order, singleton membership and acknowledged cleanup, plus measure realistic dispatch overhead independently of the pure comparison.

The CPU worker's current reserved scope is workflow-service `lib.rs`, new `inference_dependency_planning.rs`, `graph/inference_validation_state.rs`, `scheduler/readiness_lifecycle.rs`, and its tests. This contract does not touch those paths. Production integration should use its completed planning-hash candidate when available. The current production route has no Ready reordering and this contract alone is not the completed research scheduler.
